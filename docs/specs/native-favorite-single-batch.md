# 单批推荐候选人原生收藏

## Problem Statement

BOSS“推荐牛人”页面中的候选人会随着刷新或下一批推荐而消失。现有工具已经能够在普通 Chrome 页面中滚动采集候选人卡片、写入本地 SQLite，并按岗位 Screening Profile 进行 AI Initial Screening；但筛选结束后，用户若没有时间立即打招呼，就可能无法再通过平台找到这些候选人。

用户需要把 Initial Screening 合适的候选人加入 BOSS 自身的 Native Favorite，使 BOSS 收藏管理页成为可延后处理的 Favorite Pool。用户有时间时，再集中采集 Favorite Pool，进行 Secondary Screening、排序并自主决定联系对象和时间。

## Solution

在现有自动化流程中增加可选的“筛选并收藏”动作。用户为每个岗位的 Screening Profile 配置允许自动收藏的评级集合，并在启动单批任务时选择“仅采集并筛选”或“筛选并收藏”。系统完成整个 Capture Batch 的 Initial Screening 后，根据本批次锁定的配置快照生成收藏队列；Chrome 扩展在原 Source Page Context 中串行执行 BOSS Native Favorite，并把每位候选人的结果写回本地。

第一阶段仅支持由用户主动启动的单批任务。系统不会自动刷新推荐页或连续处理下一批。单批能力通过真实 BOSS 页面验证稳定后，再单独增加 Continuous Favorite Mode。

## User Stories

1. 作为招聘人员，我希望把 Initial Screening 合适的候选人加入 BOSS Native Favorite，以便刷新推荐页后仍能在平台收藏管理页找到他们。
2. 作为招聘人员，我希望在没有时间立即联系候选人时选择“筛选并收藏”，以便先建立 Favorite Pool、以后再集中处理。
3. 作为招聘人员，我希望保留“仅采集并筛选”，以便有时间时继续沿用当前即时查看和联系流程。
4. 作为招聘人员，我希望每个岗位单独配置自动收藏评级，以便不同岗位采用不同的人才标准。
5. 作为招聘人员，我希望收藏评级配置来自前端而不是执行代码常量，以便无需改代码就能调整岗位策略。
6. 作为招聘人员，我希望第一版继续使用现有 UR、SSR、SR、R、N 评级体系，以便不修改现有 Prompt 和 AI 输出合同。
7. 作为招聘人员，我希望未配置收藏评级的岗位不能启动“筛选并收藏”，以免采用隐含默认规则误收藏。
8. 作为招聘人员，我希望启动任务时看到当前岗位、筛选后动作和收藏评级，以便确认本批次采用的设置。
9. 作为招聘人员，我希望任务启动后锁定配置快照，以便运行中修改岗位配置不会改变正在执行的批次。
10. 作为招聘人员，我希望系统先完成整个 Capture Batch 的 Initial Screening，再开始收藏，以便收藏队列完整、结果容易检查。
11. 作为招聘人员，我希望只有获得有效评级且评级命中 Favorite Eligibility Policy 的候选人才进入收藏队列。
12. 作为招聘人员，我希望 AI 筛选失败、被停止或没有评级的候选人不会被收藏，以免无依据执行平台写操作。
13. 作为招聘人员，我希望只有具备可信 Platform Identity 的候选人才自动收藏，以免因同名或文本相似收藏错人。
14. 作为招聘人员，我希望身份不完整者进入人工处理结果，而不是被静默跳过，以便以后补充验证。
15. 作为招聘人员，我希望系统不因本次收藏功能重写历史候选人去重逻辑，以免破坏现有数据库和采集流程。
16. 作为招聘人员，我希望同一 Candidate 在不同岗位下保留各自的筛选结果，但平台收藏只执行一次。
17. 作为招聘人员，我希望此前已经收藏的候选人被识别并跳过写操作，以免重复请求。
18. 作为招聘人员，我希望系统区分“本次收藏成功”和“此前已收藏”，以便知道收藏状态的来源。
19. 作为招聘人员，我希望收藏动作串行执行，以降低错误关联和页面状态竞争的风险。
20. 作为招聘人员，我希望收藏动作默认间隔 3–8 秒且不能低于 3 秒，以避免短时间连续写操作。
21. 作为招聘人员，我希望首版默认最多收藏 20 人、硬上限 50 人，以降低配置错误造成的大范围误操作。
22. 作为招聘人员，我希望超出单批上限的合格候选人保留为待处理，以便以后继续，而不是丢失。
23. 作为招聘人员，我希望手动停止收藏任务时系统不再开始下一人，以便随时控制平台写操作。
24. 作为招聘人员，我希望当前正在执行的动作能够得到明确结果或进入 unknown，以免强制中断造成假失败。
25. 作为招聘人员，我希望恢复任务时只处理原配置快照中的 pending 项，以便任务可预测且不会重复收藏。
26. 作为招聘人员，我希望明确失败可以重试一次，以便处理临时页面或网络故障。
27. 作为招聘人员，我希望结果 unknown 时禁止自动重试，以免平台已经成功但本地没有收到响应时重复操作。
28. 作为招聘人员，我希望 success 和 already_favorited 在重复执行时始终跳过，以保证幂等。
29. 作为招聘人员，我希望原 Source Page Context 失效时任务自动停止，以免在错误标签页或错误批次执行收藏。
30. 作为招聘人员，我希望登录失效、验证码、频繁操作提示、权限错误或连续失败时系统自动暂停，以便尊重平台状态并避免继续扩大错误。
31. 作为招聘人员，我希望每名候选人都有收藏结果、失败原因、尝试次数和时间记录，以便审计和排查。
32. 作为招聘人员，我希望系统只添加 Native Favorite、不自动取消，以免删除我手工建立的收藏。
33. 作为招聘人员，我希望修改岗位评级或后续 Secondary Screening 结论不会自动取消既有收藏，以便清理动作始终由我决定。
34. 作为招聘人员，我希望收藏成功以候选人真实进入 BOSS 收藏管理体验为准，而不是以某个未经验证的私有接口返回为准。
35. 作为招聘人员，我希望 Cookie、平台 Token 和安全参数不离开正常登录的 Chrome 页面及本机，以保护账号安全。
36. 作为招聘人员，我希望收藏功能只在 BOSS 页面开放，以免错误地把 BOSS 身份和动作逻辑套用到猎聘。
37. 作为招聘人员，我希望现有求简历、附件下载、推荐页采集和 AI Initial Screening 不受影响，以便新功能可以安全增量上线。
38. 作为招聘人员，我希望单批功能稳定后再增加 Continuous Favorite Mode，以便连续蓄水建立在可验证的可靠基础上。

## Implementation Decisions

- 保留“普通 Chrome 页面 + Chrome 扩展 + 本地 Python API + SQLite”的现有架构；BOSS 页面不改用 Playwright 控制。
- 将 Native Favorite 作为平台状态和候选人缓冲机制，不创建可替代平台收藏的本地收藏概念。SQLite 只负责身份、任务、结果、审计和幂等。
- Screening Profile 保存该岗位的 Favorite Eligibility Policy。第一版评级候选集合固定来自现有 AI 输出合同 UR、SSR、SR、R、N，但具体选中哪些评级完全由用户配置。
- Automation Flow 保存本次“仅采集并筛选”或“筛选并收藏”的选择，以及串行间隔和单批上限。岗位规则与运行方式分开管理。
- Chrome 扩展只展示并执行桌面端已经确认的配置，不维护第二份岗位收藏规则。
- 启动单批任务时持久化配置快照，至少包含岗位、Screening Profile 及其版本、筛选后动作、收藏评级、数量上限和节流设置。任务运行中修改配置只影响下一批。
- Capture Batch 全部 Initial Screening 结束后才生成收藏任务。只有成功产生有效评级并命中配置快照的候选人才进入待收藏集合。
- 引入独立的 Platform Identity 存储，保留平台、候选人主体标识、关系标识、请求上下文标识、详情链接、来源证据及观察时间。`friendId` 表示 Recruiting Relationship，不等同于 Candidate 身份。
- 第一阶段不改变现有文本指纹候选人去重行为。平台写操作必须使用可信 Platform Identity；只有文本指纹的候选人标记为 identity-incomplete。
- 引入持久化收藏批次、收藏任务和收藏动作结果。收藏批次关联 Capture Batch、screening run 和配置快照；任务关联 Candidate、岗位及身份快照；每次动作保留方法、状态、错误分类、尝试次数和时间。
- 收藏任务状态至少区分 pending、running、success、already_favorited、failed、unknown、identity_incomplete、stopped。unknown 与 failed 的重试规则不同。
- 明确失败最多自动重试一次；unknown 不自动重试。恢复同一任务时 success 与 already_favorited 永远跳过，pending 继续，failed 仅由“重试失败项”触发。
- 收藏动作只添加、不自动取消。第一阶段不提供或调用自动取消收藏能力。
- 平台执行采用适配器隔离。技术验证先观察真实手工收藏的 DOM、请求和身份字段，再决定使用页面原生按钮或正常登录页面上下文中的同源请求；不能以 OpenCLI 参考实现代替真实验证。
- 扩展执行器绑定启动采集时的 Source Page Context。执行前验证标签页、平台、页面地址和批次上下文；上下文失效时停止并回传错误，不切换到任意 BOSS 标签继续。
- 桌面端在 Initial Screening 完成后发布收藏队列；扩展端在原标签页领取并串行执行；每项结果通过本地 API 回传，桌面端成为持久状态的事实来源。
- 本地接口继续使用 `X-Boss-Local-Token`，仅监听 loopback。新增接口应围绕“读取当前批次任务、领取下一项、回传结果、停止/状态”设计，不提供可任意指定候选人并绕过已锁定批次的通用平台写入口。
- 默认操作间隔为 3–8 秒，最低 3 秒；第一版默认单批 20 人、硬上限 50 人；全部动作串行。
- 登录失效、验证码、频繁操作提示、权限/风控错误、身份缺失、Source Page Context 失效或连续失败属于自动暂停条件。系统不实现验证码处理或平台限制绕过。
- 第一阶段仅在 BOSS 推荐牛人页面启用收藏。猎聘保持原有采集和筛选流程。
- AI Prompt、AI 输出 JSON 合同和现有五档评级语义不在本阶段修改。
- 第一阶段只实现 Single-Batch Favorite Mode。Continuous Favorite Mode、收藏管理页采集和 Secondary Screening 分别作为后续规格。

## Testing Decisions

- 测试外部行为和持久结果，不断言内部私有函数调用或具体 DOM 选择器拼接过程。
- 桌面端以完整工作流作为主测试接缝：临时 SQLite、假 AI 和本地 HTTP 接口共同模拟导入 Capture Batch、Initial Screening、根据配置快照生成任务、扩展领取、结果回传及最终汇总。
- 主工作流测试覆盖：岗位配置缺失、配置快照、评级命中与未命中、筛选失败排除、身份不完整、单批上限、停止与恢复、成功幂等、already_favorited、failed 重试一次、unknown 禁止自动重试。
- 扩展端以平台适配器作为第二个测试接缝：使用脱敏 BOSS 页面夹具和 Chrome mock 验证身份解析、Source Page Context 校验、串行执行、停止、结果分类及敏感信息脱敏。
- 本地接口测试覆盖鉴权、非法状态转换、陈旧批次结果、重复结果回传、请求体限制和错误响应。
- 数据迁移测试使用旧版本数据库结构，验证向前迁移、历史候选人数据保留和现有查询兼容。
- 回归测试覆盖现有扩展采集、精确批次 Initial Screening、求简历、附件下载和现有手动筛选页面。
- 真实平台验收不进入自动测试：在正常登录的 BOSS 推荐页对一个测试候选人进行受控收藏，并人工确认其出现在 BOSS 收藏管理页。未经该验证，不进入批量执行实现。
- 优先复用现有自动化流水线、本地接口、迁移和扩展回归测试风格；新增测试通过公开工作流接口驱动状态。

## Acceptance Criteria

1. 用户可以为每个 Screening Profile 配置 UR、SSR、SR、R、N 中任意收藏评级组合，未配置时不能启动“筛选并收藏”。
2. 用户可以选择“仅采集并筛选”或“筛选并收藏”，现有模式行为保持不变。
3. 单批运行锁定配置快照，完成整个 Initial Screening 后才生成收藏队列。
4. 只有 BOSS、有效评级命中策略、具备可信 Platform Identity 且未超过上限的候选人进入执行队列。
5. 对至少一名真实推荐候选人完成平台 Native Favorite，并能在 BOSS 收藏管理页确认可见。
6. 收藏任务串行执行，默认间隔 3–8 秒、最低 3 秒；默认上限 20、硬上限 50。
7. 每名候选人最终表现为 success、already_favorited、failed、unknown、identity_incomplete、pending 或 stopped 中可解释的状态，并保留失败原因和尝试记录。
8. 明确失败最多自动重试一次；unknown 不自动重试；重复运行不会再次操作 success 或 already_favorited。
9. 用户停止后不再启动下一项，恢复时继续同一配置快照中的 pending 项。
10. Source Page Context 失效、登录失效、验证码、平台限制或连续失败时任务自动停止或暂停。
11. 系统不自动取消任何 Native Favorite，也不因其他岗位评级变化删除收藏。
12. Cookie、平台 Token 和安全参数不会写入普通日志或发送到外部服务。
13. 猎聘收藏入口不可用，原猎聘采集筛选流程保持不变。
14. 现有推荐页采集、AI Initial Screening、求简历和附件下载回归测试通过。
15. 旧数据库可以安全迁移，历史候选人和筛选记录不丢失。

## Out of Scope

- 自动刷新推荐页并持续处理下一批的 Continuous Favorite Mode。
- BOSS 收藏管理页识别、滚动采集和资料补全。
- Favorite Pool 的 Secondary Screening、P0–P3 联系优先级和联系队列。
- 自动打招呼、自动发送消息或自动建议联系时间。
- 自动取消收藏或收藏池自动清理。
- 修改 UR、SSR、SR、R、N 的评分语义、Prompt 或输出 JSON 合同。
- 全面重写历史候选人文本指纹去重及已有数据库身份合并。
- 猎聘或其他招聘平台的原生收藏适配。
- 验证码处理、平台限制规避或高并发平台写操作。

## Further Notes

- OpenCLI 的标签实现只能作为身份字段和请求形态的调查线索。其流程先从聊天关系查找候选人，不能证明推荐页未沟通候选人可以直接收藏。
- 开发必须先完成真实页面身份字段调查和单人收藏实验。若推荐页未沟通候选人无法建立 Native Favorite，应停止实现并输出技术验证结论，而不是改成自动打招呼或本地收藏来绕过目标。
- 本规格使用根目录领域词汇和相关 ADR：Native Favorite 是平台状态；Platform Identity 与 Recruiting Relationship 分离；平台写操作不使用文本指纹身份。
